# Radio Friday

Next.js + Go/Gin + TypeScript Agent (OpenAI Agents SDK + Zod), PostgreSQL and Redis.
Chat uses durable asynchronous replies: send succeeds immediately, validated message bubbles appear later and unsent bubbles can be interrupted.

## Local development

Use Node 22 and a Go version compatible with your OS (recent Go on macOS 26).

```bash
nvm use 22
pnpm install
pnpm db:up
```

For a new checkout, copy `apps/server/.env.example` to `apps/server/.env`,
`apps/agent/.env.example` to `apps/agent/.env`, and merge `apps/web/.env.example` into `apps/web/.env.local`.
Set a random JWT secret, and the **same** random `AGENT_TOKEN` in server and agent environments.
Model credentials belong only in `apps/agent/.env`. Database access, including novels and chapters, belongs to the Go API.
Never overwrite existing local environment files blindly.

Stop earlier dev processes first, then start all four application processes:

```bash
pnpm dev:all
```

Open http://localhost:3011. API and worker automatically apply versioned SQL migrations.
Redis and PostgreSQL must already be running. If you already have PostgreSQL on 5432,
keep using that instance and start only Redis with `docker compose up -d redis`.

The web development server uses `apps/web/.next-dev`; production builds and
`next start` use `apps/web/.next`. This keeps builds from deleting scripts needed
by an open development page. Tests can select a separate directory with `NEXT_BUILD_DIR`.

The Go API and worker do not hot-reload. After changing Go routes or migrations,
restart `pnpm dev:all`; refreshing the Next.js page alone leaves the old API running.
For schema changes, add a new numbered migration. Editing an already applied SQL
file does not update existing databases because `schema_migrations` records its filename.

Alternatively run each process in its own terminal:

```bash
pnpm server:dev   # Go HTTP API :8080
pnpm worker:dev   # durable generation + delivery jobs
pnpm agent:dev    # TypeScript Agent :8081
pnpm dev          # Next.js :3011
```

LiveKit rooms, join tokens and agent dispatches are served by the Go API.
Set the optional `LIVEKIT_*` settings in `apps/server/.env`, then run `pnpm livekit:up`.
The browser accesses rooms through the same-origin `/api/v1/rooms` proxy.
Anyone can list rooms and watch. Logged-in users can create rooms; only a room's
creator joins as its host and can close it or manage agent dispatches. Other
logged-in users join as viewers, just like guests. Ownership is stored in LiveKit
room metadata; old rooms without ownership metadata must be recreated to host.
Participant identities and roles are generated by Go from the session and room
owner, rather than accepted from the browser.
Each account may have only one open room. Creation and closure share a PostgreSQL
advisory lock; a Redis reservation records the owner's current room before the
LiveKit call, surviving API restarts and delays in the cloud's global room list.
Uncertain creates retry with the same room ID. Local tests use a process store.
An existing room returns `409 room_already_exists` with its `item`; the lobby
shows an entry link instead of a second creation form. Closed or expired rooms
release the slot after an exact-name lookup confirms they are gone.
Only one page/device may enter an account's own room. Admission is reserved on
the server before a host token is issued; a second page receives
`409 host_session_in_use`, without a viewer token or an automatic takeover.
The same account can still watch other people's rooms in another page/device.
Navigating away from the actual host page disconnects that host and ends its
room; refreshing is not a supported way to transfer or resume a broadcast.
LiveKit's native reconnection can recover while the original participant has
not left. Muting devices, inactivity and background tabs do not end a room when
the host connection remains active.

After a host has connected, its confirmed departure closes the entire room,
including remaining viewers and agents. New rooms that no host has joined yet
continue to use the existing LiveKit empty-room timeout; no extra departure
grace period or new LiveKit timeout override is added. The API stores the active
host session and closing state in Redis, and retries failed closes before
releasing the owner's room slot. `GET /api/v1/rooms/:roomId` distinguishes an open,
closing or closed room so clients do not offer to rejoin an ended broadcast.

Configure **LiveKit Cloud → Settings → Webhooks** to send events to
`https://<public-go-api-host>/api/v1/livekit/webhook`, using the same signing API
key as `LIVEKIT_API_KEY`. This is the Go API endpoint, not a browser callback or
the web app's authenticated API proxy. It authenticates the raw request body,
deduplicates successfully processed events and checks current room/participant
SIDs before acting on notifications. Room, participant and track events update
the shared Redis snapshots. There is **no periodic full-room LiveKit sweep**.
API startup performs one synchronization; explicit refreshes perform a shared,
rate-limited synchronization. Only rooms already marked `closing` have persisted
retry tasks, with increasing delays; restarting the API resumes those tasks.
Failed reads do not prove that a host left, and never cause a room to be deleted.
If LiveKit ultimately abandons an event and no later event or explicit check
corrects it, state can remain stale. Webhook configuration is therefore required
for automatic host-departure handling; WebSocket delivery cannot discover a
change that the backend never received.

The lobby and room page obtain a connection URL from same-origin
`POST /api/live/connection`, then connect directly to the Go API's
`/api/v1/rooms/socket`. The server exchanges the existing login cookie for a
60-second read-only ticket scoped to the lobby or selected `roomId`; each reconnect
gets a new ticket. The long-lived login credential stays HttpOnly. The public
WebSocket origin is derived from server-side `COMPANION_API_URL`; set
`COMPANION_WS_URL` only when that API URL uses an internal address.
Matches and conversation sockets likewise bootstrap through `POST /api/realtime/connection`
and connect directly to Go using 60-second tickets bound to the account, origin
and exact socket path. Conversation access checks still run before the handshake.
Deploy the Go ticket endpoints before deploying the frontend.
Initial connections and reconnects receive a full snapshot. Guests can receive
public data; `canManage` is computed per connection from the verified ticket.
Snapshots remain in React Query, and an incoming
push cancels stale HTTP reads. Ordinary list/detail reads and WebSocket snapshots
do not query LiveKit. The previous five-second lobby, detail and voice polling
has been removed. `POST /api/v1/rooms/refresh` and
`POST /api/v1/rooms/:roomId/refresh` explicitly verify upstream state; repeated
requests are coalesced and limited rather than multiplied by viewer count.

Use separate PostgreSQL, Redis and LiveKit environments for local development
and production. Sharing a LiveKit Cloud project shares its room list, even when
the frontend URLs differ. Local Docker LiveKit is the default development setup.
For local development using a separate LiveKit Cloud test project, automatic
notifications require a public HTTPS tunnel forwarding to the local Go API on port 8080, with
`/api/v1/livekit/webhook` configured in Cloud. A localhost callback cannot be
reached from Cloud. Alternatively, local Docker LiveKit already points to
`http://host.docker.internal:8080/api/v1/livekit/webhook`; restart LiveKit after
changing that configuration. The Go API and agent must use the matching local
LiveKit URL/key pair when choosing this mode. No new application secret is needed.

Each room has one viewer call slot: submitting a request reserves it immediately,
including while approval is pending or the approved viewer is muted. There is no
queue. A host can approve, reject, or end the call; the viewer must explicitly
enable each device after approval and can cancel or hang up. Approved viewers
can publish microphone audio and camera video, shared with everyone in the room;
screen sharing remains prohibited. Viewers initially see only a call request
button. Approval reveals a separate personal call panel with camera preview,
microphone/camera switches (both off by default) and an exit action. Ending the
call or losing permission stops both devices and returns the viewer to watching.
Voice state and actions live under `/api/v1/rooms/:roomId/voice`: `GET /`,
`POST /request`, `DELETE /request`, `POST /requests/:requestId/approve`,
`POST /requests/:requestId/reject`, and `POST /end`. Actions carry a `requestId`;
the join response supplies a two-hour `voiceToken` sent as `X-Live-Voice-Token`.
Host actions also require the login session. Expired voice credentials require
rejoining. State is stored in server-managed LiveKit participant attributes, with
PostgreSQL advisory locks for cross-replica admission; no schema migration is needed.
LiveKit attribute and permission events update call controls. Entering a room,
SDK reconnection and user actions perform authoritative checks; no five-second
voice poll runs in the browser or API. Host departure closes the room and ends
its call. Real voice tests run with
`LIVEKIT_INTEGRATION=1 pnpm --filter web exec playwright test tests/live-voice.spec.ts`
using a local Go fixture, Chrome/Chromium and temporary LiveKit rooms.
Agent dispatch requires a separately
running LiveKit Agents worker; `apps/agent/src/legacy-livekit.ts` is only a health-check placeholder.
Novel reads, writes, ownership checks and draft visibility are also handled by Go.
Next.js contains page rendering, form-to-API adapters and a same-origin API proxy; it does not connect to the database.
See [deployment](DEPLOYMENT.md) for API, worker and Agent deployment.
