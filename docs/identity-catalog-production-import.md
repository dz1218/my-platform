# 线上完整人物库导入指南

本流程把项目的 `apps/server/config/identities.json` 导入线上 Supabase，供部署在 Railway 的后端读取。在电脑上的项目终端执行即可，不需要把资料上传到 Railway，也不需要修改本地 `.env`。

## 为什么线上只有三个人

后端首次执行 `001_companion.sql` 时，会创建林晚、苏禾、陈念三个初始角色。部署代码不会把本地数据库同步到 Supabase，也不会自动执行完整人物库导入。

完整资料文件包含 100 个职业、1,000 位角色。导入决定线上有哪些人物以及他们的人设；Agent 和 Worker 的部署负责生成和处理回复，两者需要分别完成。

## 执行前确认

- 在 VS Code 集成终端或 macOS 终端操作，进入当前项目根目录。
- 电脑可运行 Go 和 pnpm。项目要求 Node `>=22 <25`，建议使用 Node 22。
- 线上 API 已成功完成数据库迁移。导入工具不会自动迁移；如果提示缺表、缺字段，先检查 API 部署和迁移日志。
- 准备与 Railway API 相同的线上 `DATABASE_URL`，并确认目标是要更新的 Supabase 项目。
- 正式导入会修改线上人物及相关会话状态，应在可接受的时间执行，并准备可恢复的数据库备份。

## 第一步 进入项目根目录

```bash
cd '/Users/daizhuo/Desktop/  /my-platform'
```

如果终端已经位于该目录，可以跳过。命令需要从根目录运行，因为 `package.json` 在这里定义了导入脚本。

## 第二步 开启临时 shell

```bash
zsh
```

这会创建一个子 shell。之后设置的线上数据库变量只在这个子 shell 及其启动的程序里使用；最后执行 `exit` 即可返回原来的环境，避免后续本地开发继续使用线上数据库。

如果已执行过这一步，且仍在同一个终端会话中，不需要再开一层。

如果使用 nvm，可以在这个子 shell 中切换版本：

```bash
nvm use 22
```

截图中 Node 25 的 `Unsupported engine` 是版本警告，校验和预览实际已成功；它本身不能证明导入卡住。切换版本是为了遵循项目运行要求。

## 第三步 指定线上数据库

先复制 Railway API 的完整 `DATABASE_URL`，在下面命令中替换占位内容：

```bash
export DATABASE_URL='替换为线上完整数据库连接串'
```

连接串格式示例：

```text
postgresql://postgres.PROJECT_REF:URL_ENCODED_PASSWORD@POOLER_HOST:5432/postgres?sslmode=require
```

这里使用 Supabase Session pooler 的 URI。密码中的特殊字符需要 URL 编码；已经编码的 `%40` 等内容保持原样，不要再次编码。`sslmode=require` 要求使用加密连接。

`export` 使后续导入进程读到该变量。导入程序优先使用进程环境变量，再加载 `.env` 中尚未设置的值，因此不用修改本地文件。不要跳过这一步直接导入，否则可能连接本地数据库。

文档中的连接串是模板，不是可直接使用的真实凭证。

## 第四步 校验资料文件

```bash
pnpm identities:validate
```

这一步只读取并校验资料，不连接数据库，用于提前发现格式错误、重复 ID、职业引用等问题。

完整资料的成功结果类似：

```json
{"complete":true,"identities":1000,"occupations":100,"valid":true}
```

看到 `valid: true` 后再继续；若报错，先修复资料，不执行正式导入。

## 第五步 预览线上变化

```bash
pnpm identities:preview
```

这一步连接刚才指定的数据库，使用只读事务比较现有记录与资料文件，不修改人物、版本或任务。

本次会话中已确认的预览结果是：

```json
{"created":997,"updated":3,"unchanged":0,"affectedConversations":1,"dryRun":true}
```

| 字段 | 含义 |
|---|---|
| `created` | 将新增的人物数 |
| `updated` | 相同 ID 但资料需要更新的人物数 |
| `unchanged` | 资料已经一致的人物数 |
| `affectedConversations` | 因人物变化而需要更新上下文或任务状态的已有会话数 |
| `dryRun` | `true` 表示仅预览，没有写入 |

这个结果表示会新增 997 人、更新原三人，并影响一个已有会话。这里的“影响”不是删除聊天记录：已有消息保留，但派生摘要会重置，旧人设下待生成或待投递任务可能取消，并按现有托管规则重新排队。

每次导入以当次预览为准，不要把上述数字当成所有数据库必然出现的结果。

## 第六步 正式导入

```bash
pnpm identities:import
```

在同一终端中执行，确保仍使用第三步设置的线上连接。

工具按角色 ID 插入或更新，不是按姓名重复创建。未包含在文件中的其他人物会保留。整批更新放在一个事务中，成功提交后才整体生效；相同资料重复导入不会重复新增或无故递增人设版本。

命令没有逐条进度输出，通常要等结束才打印 JSON。因此光标停在空白行不等于程序已卡死。实际写入包含数据库往返、锁等待和会话更新，可能比只读预览慢。

成功时会输出结果，`dryRun` 为 `false`，并返回终端提示符。若只看见执行命令而没有结果，不能宣称导入成功。

## 第七步 再次预览确认

```bash
pnpm identities:preview
```

对于未再修改的完整资料，预期关键字段为：

```json
{"created":0,"updated":0,"unchanged":1000,"affectedConversations":0,"dryRun":true}
```

这证明资料文件中的 1,000 人已经与数据库一致，不代表数据库绝对只有 1,000 人，因为文件之外的角色不会被删除。

随后刷新线上人物页面。导入成功无需重建前端；如果页面仍只有三人，确认 Vercel 连接的 API 与这次导入使用的是同一个 Supabase 数据库，并检查接口响应和缓存。

人物出现不代表 AI 回复链路已通过验证，仍需确认 Agent、Worker 正常运行并实际发送一条消息测试。

## 第八步 退出临时环境

```bash
exit
```

这只退出第二步创建的子 shell，不会撤销已经提交的导入。其设置的线上 `DATABASE_URL` 不会传回父 shell。如果父 shell 原本就有数据库变量，退出后恢复的是父 shell 原有环境。

## 看似卡住或导入失败时

导入命令在解析资料后，为数据库连接和导入操作共设置两分钟超时；Go 编译和此前的文件读取不包含在这两分钟内。因此两分钟不是整个终端命令的严格结束时限。

1. 没有结果时不要并行启动第二次导入。正式导入有事务级锁，重复运行可能只会增加等待。
2. 若出现错误，保存完整输出。`context deadline exceeded` 表示超时，但不能仅凭它断定是网络慢还是锁竞争。
3. 如果已经等待数分钟仍没有输出，可以按 `Ctrl+C`，然后在同一个终端运行 `pnpm identities:preview` 核对状态。
4. 若预览为 `created=0、updated=0、unchanged=1000`，说明数据库中的资料已一致，不必重跑。
5. 若仍为原来的 `created=997、updated=3`，说明目标资料尚未完成导入。确认原进程已经结束，定位连接、锁等待或超时问题后再重试。
6. 若结果既不是原值也不是全部一致，检查目标库、资料文件及其他写入操作，不要直接推断为本工具提交了半批数据。

事务提交前出错通常会回滚；提交附近连接中断时，客户端可能无法确认提交结果，所以应以重新预览为准。不要为排查导入问题清空人物表或迁移记录。

如果重复在两分钟左右超时，应检查导入性能或超时设置。当前命令没有延长超时的参数，不要反复盲目重跑。
