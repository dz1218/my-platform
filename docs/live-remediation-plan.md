# 直播功能技术整改方案

制定日期：2026-10-18。状态：本轮范围内代码及本地验收完成；未发布线上，锁优化开关默认关闭。

对应审查记录：[直播功能问题清单](./live-audit.md)。下文记录实施约定；实际完成情况、测试范围及发布限制见文末，不能将本地验收等同于线上发布。

## 范围与约束

- 本方案处理问题清单第 1、3、4、6、7 项，按三个阶段实施和验证。
- **问题 2（连麦凭证续期）、问题 5（直播 AI 助手）暂不解决，保留当前实现与入口，不顺带修改。**
- 保留现有 LiveKit、Go、React Query 和 Zustand 架构。
- 桌面和手机共用业务宿主；UI 遵循 [frontend.md](./design/frontend.md) 的 Tailwind v4、语义 token、无 hover 下划线及包边界约定。
- 刷新后自动恢复房间连接，摄像头和麦克风默认关闭；不持久化设备开关、房间令牌或账户草稿。
- 不新增直播聊天历史存储，不自动提高 50 人房间上限。

## 第一阶段：修复生命周期与关闭流程

### 1. 明确房间和连接状态

保留房间状态：

```ts
type RoomState = 'open' | 'closing' | 'closed';
```

新增主播连接状态及服务端恢复期限：

```ts
type HostConnection = 'waiting' | 'connected' | 'reconnecting';

type RecoveryFields = {
  hostConnection?: HostConnection;
  reconnectDeadline?: number; // Unix 毫秒
};
```

字段随详情接口及现有房间 WebSocket 快照返回。旧记录缺少字段时兼容读取，不要求数据库表迁移。

| 场景 | 处理 |
|---|---|
| 已连接主播刷新、断网、崩溃、关闭标签页 | 服务端确认离线后进入 60 秒恢复期 |
| 期限内确认主播重新连接成功 | 取消到期任务，继续原房间 |
| 到期仍未恢复 | 核实后进入关闭流程 |
| 主播明确确认结束 | 立即接受关房，不进入恢复期 |
| 观众离开 | 不关闭房间 |

首次离线确定截止时间。重复事件、加入请求和详情刷新不得延期；领取令牌不等于恢复成功。已经进入 `closing` 的房间不能通过重连恢复开放。

初次尚未连接成功的预约与已开播后的恢复期分开处理。保留现有预约保护，但返回可重试的等待状态和预约到期时间，前端不再永久阻止重新加入。

浏览器后退、地址栏跳转等未经过站内确认的离开统一按断线处理，不新增全局浏览器导航拦截。

### 2. 服务端持久化恢复任务

在现有 Redis 生命周期数据和维护循环中增加到期核验队列：

- 生命周期、截止时间、队列和更新通知同步写入。
- 到期获取房间锁，重新核对房间 SID、当前主播会话和在线状态。
- 当前有效主播已恢复则取消任务，否则转入既有关房流程。
- 查询失败退避重试，不能把服务错误当作主播离线。
- 多实例共享队列与数据库锁，进程重启后继续执行。
- 到期任务取消或执行前必须重读状态，避免旧任务关闭新会话。

新房间显式设置 LiveKit `departureTimeout` 为 120 秒，避免单主播刷新时底层房间提前回收；首次空房等待保持现有 600 秒。已被底层销毁的房间不自动重建成另一场直播。

参数依据：[LiveKit CreateRoomRequest 协议](https://github.com/livekit/protocol/blob/main/protobufs/livekit_room.proto)。它们是底层空房回收参数；业务恢复窗口仍由服务端持久化的 60 秒截止时间控制。

已有房间不强制删除；不能仅凭新创建参数变更就宣称旧房间的回收配置也已更新。

### 3. 主播入场与前端恢复

- 同一房主、原房间仍开放且旧连接已离线时，允许在恢复期限内建立新会话。
- 旧主播仍在线时保持占用限制，不通过重连踢走其他页面。
- 普通新开页面被占用拒绝后不自动接管；占用期间的自动等待仅用于浏览器刷新、当前页面的断线恢复，等待有次数上限。
- 入场预约使用 `attemptId` 保证幂等；旧 identity、参与者 SID 和房间 SID 的事件不得影响新会话。
- SDK 原生重连优先；最终断开后再销毁旧资源并重新加入，禁止两个恢复流程同时连接。
- 暂时性错误按 1、2、4、5 秒退避，后续间隔上限 5 秒并加入抖动；遵守服务端期限及 `Retry-After`。
- 预约等待遵守独立的预约期限；不要用恢复期的 60 秒提前截断现有 90 秒预约。
- 恢复期间的新令牌有效 10 秒、预约保护 15 秒，且不超过原恢复截止时间，给连续刷新留下再次领取机会；初次开播的 60 秒令牌、90 秒预约保持不变。
- 关闭、不存在和认证失效立即停止重试。离页、换账户、换房间时清理请求和计时器。

已确认的设备规则：**刷新后自动恢复房间连接，摄像头和麦克风保持关闭。** 不保存设备开关、令牌或账户草稿。同一页面内 SDK 原生重连继续沿用其媒体恢复行为。

### 4. 观众等待体验

- 保留房间连接、标题、成员列表和聊天区。
- 主播画面显示“主播连接暂时中断，正在等待恢复…”，移除失效视频。
- 主播恢复但未开摄像头时显示“等主播开启画面”，避免继续显示断线提示。
- 观众无需刷新；重新发布媒体后自动播放，必要时保留播放声音入口。
- 沿用主播离线后撤销连麦批准的规则；恢复后重新申请。
- 不新增聊天历史存储，刷新后的主播不补回离线期间消息。

业务状态使用作用域内 Zustand；房间快照仍归 React Query；SDK、AbortController 和计时器仍由应用层负责。桌面和手机不得各自建立第二套连接或恢复流程。

### 5. 统一关房接口语义

继续使用原关闭接口，调整返回规则：

| 结果 | 返回与前端处理 |
|---|---|
| 已完成关闭 | `200`，状态为 `closed` |
| 关闭意图已持久化，清理仍在执行 | `202`，状态为 `closing` |
| 尚未接受关闭 | 明确错误，允许重试 |
| 响应丢失或超时 | 查询当前状态，不直接认定失败 |

所有权校验与房间是否开放分开：房主重复关闭 `closing / closed` 房间，返回当前状态；非房主仍拒绝。

`closing` 表示已经结束业务上的直播：禁止重新加入、停止前端媒体并显示结束状态。底层删除失败由后台重试，不恢复开放。

返回大厅复用同一个关闭动作：

- 主播弹出“返回大厅将结束当前直播，是否继续？”
- “继续直播”关闭弹窗。
- “结束并返回大厅”在确认服务端已接受关房后跳转。
- 未接受或结果未确认时留页，展示准确状态。
- 观众、已结束页面和未获得主播会话的占用页直接返回。

返回入口不能仅凭账户拥有该房间就关闭另一页面正在使用的主播会话。身份尚未确认时等待确认结果；提交期间防止重复操作。

房间页的关闭请求携带本次入场的 `hostIdentity`，后端在锁内校验当前会话；大厅主动管理关闭仍使用账户所有权。这里不复用有两小时期限的连麦凭证，凭证续期仍不在本轮范围。

## 第二阶段：补齐状态恢复与基础限流

### 6. 状态同步补偿

保留 WebSocket 推送，不增加前端固定轮询。

新增：

- 启动同步失败后按 1、2、5、10、30 秒退避重试，上限 30 秒。
- webhook 继续作为主要更新来源。
- 客户端发现主播离开、SDK 重连完成时，调用已有受限核验接口进行一次补偿。
- 服务端对已确认开播且未关闭的房间安排每 60 秒一次的低频核验，使用共享到期队列；普通房间读取仍只读缓存。
- `waiting` 房间同样进入持久化核验队列，创建后在首次空房期限到达时核对 LiveKit；未销毁且仍有人等待的房间继续低频核验。即使 `room_finished` webhook 丢失，也能清理已销毁的空房快照及预约。查询失败只退避，不能当作空房已销毁。
- 核验任务跨实例去重，每实例最多两个并行任务；错误退避，不能立即反复执行。

低频核验增加少量 LiveKit 请求，用于修复事件遗漏。60 秒恢复期仍从服务端确认离线起算；事件丢失时，实际发现离线可能更晚。

### 7. 接口频率与连接数量控制

复用现有 Redis 限流能力，覆盖 `/rooms` 和 `/api/v1/rooms` 两套路由，避免别名绕过。

初始参数作为可配置默认值：

| 入口 | 默认限制 |
|---|---|
| 加入房间 | 每账户每分钟 30 次；访客每 IP 每分钟 120 次 |
| 连麦写操作 | 每参与者每分钟 30 次 |
| 连麦状态读取 | 每参与者每分钟 60 次 |
| 状态票据签发及连接建立 | 每账户每分钟 60 次；访客每 IP 每分钟 120 次 |
| 状态连接并发 | 每账户 10 条；访客每 IP 100 条 |
| 创建、关闭请求 | 每账户每分钟 20 次 |

补充要求：

- 参与者级限制必须基于服务端验证后的身份，不能信任客户端随意提供的 ID。
- 另设宽松 IP 总量限制，防止通过反复获取新参与者身份绕过限制。
- 并发连接用带过期时间的租约计数；正常断开释放，进程异常退出后自动过期。
- 超限返回 `429` 和 `Retry-After`，前端遵守等待时间。
- 核对部署代理的可信来源，不能直接信任任意 `X-Forwarded-For`，也不能把全部代理流量误算成一个访客。
- 参数通过正常刷新、多人重连测试调整，不把初始值视为已验证的生产容量。

直播聊天单独处理：本阶段增加接收端按发送者限频，保护页面免于刷屏；明确这不减少 LiveKit 上游流量。服务端强制禁言、封禁和消息限流需要独立的管理及消息通路设计，不能把 HTTP 接口限流当成数据通道治理已经完成。

## 第三阶段：独立优化跨房间并发

问题清单第 7 项不与生命周期修复混合发布，先记录锁等待和 LiveKit 耗时，再进行锁范围调整。

目标是不同账户、不同房间可以并行，同时保持一人一个房间和名称唯一性。

具体方案：

- 创建按账户加锁，再按实际房间名称和房间 ID 加锁。
- 关闭使用同样的账户、名称、房间锁顺序，避免锁顺序相反产生死锁。
- 普通房间核验继续只持房间锁；需要完成跨资源关闭时先释放，再按统一顺序重新加锁并核对状态。
- 新增 Redis 房间名称预约，名称比较保持现有不区分大小写的语义；创建前预约，结果不确定时保留，确认关闭后按房间 ID 校验释放。
- 同时新增按房间 ID 的持久预约，绑定账户及原始名称。API 支持自定义 ID，账户锁和名称锁不能阻止另一账户在创建超时后用不同名称占用同一 ID；请求锁释放不等于预约释放。
- 账户、名称、房间 ID 预约同步写入；未知创建结果保留三者，重试复用原 ID 和名称；释放时同时校验账户与房间 ID。不能只依赖可能滞后的 LiveKit 房间列表判断名称或 ID 是否可用。
- 发布时先完成存量名称和 ID 预约回填，包括结果尚未确认的账户预约，再启用新锁；旧、新锁规则不得同时处理写入。锁优化单独开关启用，默认维持原锁规则。
- 发现存量重名时保留原房间并阻止该名称的新建，不自动删除房间。

保留 50 人房间上限，补充房满提示；扩容需另行压测。

## 验收与实施顺序

1. 先实现生命周期、主播恢复和关闭接口，验证返回大厅。
2. 再实现同步补偿及限流。
3. 最后独立验证锁范围优化。
4. **问题清单第 2、5 项不进入上述实施阶段。**

### 必要验收场景

- 单主播刷新、有观众时刷新、连续刷新、初次连接中刷新。
- 60 秒内恢复、超过期限、到期与恢复同时发生。
- 旧事件迟到、多页面并发、预约请求响应丢失。
- 关闭成功、已接受但删除失败、响应丢失、重复关闭。
- webhook 遗漏、初始化失败后恢复、服务重启、多实例同时处理任务。
- 创建后从未开播、空房被底层销毁且 webhook 遗漏，自动核验最终清理快照与预约。
- 等待期间观众聊天可用，刷新后的设备默认关闭。
- 返回大厅取消、确认、失败及结果不确定时的行为；观众离开不关房。
- 正常重连不被误限流，异常请求被拒绝，并发连接租约可回收。
- 慢房间操作不阻塞无关账户；同账户创建和同名创建仍正确互斥。
- A 创建超时后 B 用不同名称请求同一 ID 被拒绝；A 可以沿原预约恢复；进程重启不丢失 ID 保护。
- 桌面与手机切换、Strict Mode 和组件卸载不产生重复连接或遗留设备。

运行 Go、client-core、类型检查、客户端边界检查及相关 Playwright 回归。真实 LiveKit 验收覆盖桌面和手机，并至少执行一项真实 60 秒超时测试。

### 配置与分阶段启用

- `LIVE_ROOM_LIMITS`：Go 环境中的 JSON 对象，只需填写覆盖项；未知项、非正整数和超过 100000 的值启动时拒绝。参数名为 `join_account`、`join_guest`、`voice_write`、`voice_read`、`socket_account`、`socket_guest`、`connections_account`、`connections_guest`、`mutation_account`、`ip_total`。默认值见上文，IP 总量默认每分钟 1200 次；票据签发和 WebSocket 建连共用 socket 频率预算。
- `LIVE_ROOM_SCOPED_LOCKS=false`：默认保留全局写入锁，持久化账户、名称及 ID 预约仍然启用。第三阶段代码已准备，通过独立开关分阶段启用。
- 切换 scoped 模式前应停止旧版写入者，并使全部新版 API、维护进程采用一致配置。代码先在旧全局锁下回填，再写入共享模式门禁；模式不一致的新版写入者会拒绝操作。**启用后不能直接将某个实例切回 false**；回滚必须停写、统一实例配置并核对共享模式与预约。原始旧二进制不认识门禁，不可混跑。
- `TRUSTED_PROXY_CIDRS`：Go 信任的实际反向代理出口 CIDR，以逗号分隔；默认不信任代理头。Next 票据桥接可配置 `LIVE_TRUSTED_CLIENT_IP_HEADER`，仅转发已验证由入口代理覆盖的单个 IP；Go 还需信任该 Next 服务的连接来源。浏览器直连 Go WebSocket 的代理链也需要单独核对。未经核对不填宽泛网段、不直接信任浏览器提供的 XFF。
- 当前没有核验线上代理链。默认关闭代理信任时，经过同一代理的访客可能共享预算，必须在发布时验证实际 IP 识别后再调整限额。

示例见 [Go 环境配置](../apps/server/.env.example) 和 [Web 环境配置](../apps/web/.env.example)。本轮没有修改真实环境文件或启用生产开关。

### 实际实现与验收记录

2026-10-18 本地实现包括：

- 生命周期与自动补偿：[lifecycle.go](../apps/server/internal/livekit/lifecycle.go)、[recovery.go](../apps/server/internal/livekit/recovery.go)、[maintenance.go](../apps/server/internal/livekit/maintenance.go)。重复/乱序的同一会话 joined 事件不会抹掉恢复期限；到期核验会重新检查有效主播。
- 持久化预占与锁：[reservations.go](../apps/server/internal/livekit/reservations.go)、[mutation_lock.go](../apps/server/internal/livekit/mutation_lock.go)。名称沿用 Unicode 不区分大小写语义；存量重名保留多个占用成员，未知创建保留 ID 和原始名称。
- 限流与连接租约：[limits.go](../apps/server/internal/livekit/limits.go)。租约 90 秒过期、20 秒续租，断连释放；前端遵守 `Retry-After`，等待期间离线再上线也会恢复计时。
- 前端恢复与关闭：[业务动作](../packages/client-core/src/live/room/slices/operations.ts)、[连接宿主](../apps/web/src/components/live/use-live-room.ts)。房间页及大厅关闭响应丢失都会查询状态；未确认时保留页面和错误提示。
- 接收端聊天限频：每发送者每 10 秒最多 20 条，最多保留 200 个发送者计数桶。只保护本地渲染，不限制 LiveKit 上游数据流量。
